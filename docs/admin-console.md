# 관리자 콘솔

`admin/`이 제공하는 관리자 콘솔의 화면 구성과 권한 경계, 인증 흐름, 상태 표시 원칙을 정리합니다.

## 화면과 호출 API

관리자 콘솔은 로그인한 다음 여덟 개 화면으로 구성됩니다. 회원가입 기능은 없습니다. 계정은 최고 관리자 권한을 가진 사용자만 만들 수 있습니다.

| 화면 | 파일 | 호출하는 API |
|---|---|---|
| 운영 개요 | `admin/src/pages/DashboardPage.tsx` | `GET /admin/api/settings/stats/overview`, `GET /admin/api/services`, `GET /ready`, `GET /admin/api/observability/alerts` |
| 서비스 | `admin/src/pages/ServicesPage.tsx` | `GET /admin/api/services`, `GET /admin/api/services/stats`, `POST /admin/api/services`, `POST /admin/api/services/reload`, `POST /admin/api/services/health-check-all` |
| 서비스 상세 | `admin/src/pages/ServiceDetailPage.tsx` | `GET /admin/api/services/{id}`, `PUT /admin/api/services/{id}`, `DELETE /admin/api/services/{id}`, `GET /admin/api/services/{id}/health`, `POST /admin/api/services/health-check-all` |
| 사용자 | `admin/src/pages/UsersPage.tsx` | `GET /admin/api/users/`, `POST /admin/api/users/`, `PATCH /admin/api/users/{id}`, `PUT /admin/api/users/{id}/activate`, `PUT /admin/api/users/{id}/deactivate`, `DELETE /admin/api/users/{id}` |
| API 키 | `admin/src/pages/ApiKeysPage.tsx` | `GET /admin/api/api-keys/`, `POST /admin/api/api-keys/`, `DELETE /admin/api/api-keys/{id}`, `POST /admin/api/api-keys/{id}/rotate`, 소유자 이름을 채우려고 `GET /admin/api/users/`도 함께 호출합니다 |
| 백업 | `admin/src/pages/BackupsPage.tsx` | `GET /admin/api/observability/backups` |
| 관측 | `admin/src/pages/ObservabilityPage.tsx` | `GET /admin/api/services`만 호출하고, 나머지는 Grafana로 이동하는 링크로 처리합니다 |
| 운영 설정 | `admin/src/pages/SettingsPage.tsx` | `GET /admin/api/settings/` (읽기 전용), `GET /release.json` (콘솔 번들과 함께 배포한 정적 파일) |

이 API 경로들의 타입 정의와 호출 함수는 `admin/src/services/api.ts`에 모여 있습니다. 표에서 `/admin/api`로 시작하지 않는 경로는 두 개입니다. `GET /ready`는 관리자 API가 아니라 게이트웨이 루트에 있고 인증 헤더를 요구하지 않으므로, 인터셉터가 붙지 않은 별도의 axios 인스턴스로 보냅니다. `GET /release.json`은 서버에 보내는 요청이 아니라 콘솔 자신의 번들 옆에 놓인 정적 파일을 읽는 요청이며, `admin/src/services/release.ts`가 플랫폼의 `fetch`로 처리합니다.

서비스 목록에서 서비스 이름을 누르면 `/services/{id}` 주소의 상세 화면으로 이동합니다. 상세 화면은 게이트웨이가 저장한 등록 내용을 모두 보여주고, 수정과 삭제, 마지막으로 기록된 상태 확인을 한자리에서 처리합니다. 수정 요청은 값이 바뀐 항목만 담아서 보냅니다. 서버가 `exclude_unset`으로 요청 본문을 해석하기 때문에, 보내지 않은 항목은 저장된 값을 그대로 유지합니다. 서비스 이름은 서버의 수정 스키마가 받지 않는 항목이라서 상세 화면에서도 읽기 전용으로 표시합니다. 삭제를 확인하는 대화 상자는 게이트웨이를 거치는 요청이 곧바로 404를 받게 된다는 점을 문장으로 알려주고, 삭제가 끝나면 목록 화면으로 돌아가면서 서비스 관련 질의를 모두 무효로 만듭니다. 삭제 응답은 본문이 없는 204가 아니라 `service_id`와 `service_name`, 등록부 재적재 결과를 담은 200이기 때문에, `deleteService()`는 이 본문을 해석해서 목록 화면으로 넘겨줍니다.

## 권한 경계

`admin/src/services/api.ts`가 정의하는 역할 순서는 `user < moderator < admin < super_admin`입니다. 화면에서는 이 순서를 다음과 같이 사용합니다.

- `admin` 이상은 사용자 목록을 조회하고, 서비스와 계정의 활성 상태와 비활성 상태를 바꿀 수 있습니다.
- `admin` 이상은 서비스를 등록하고 수정하고 삭제할 수 있습니다. Bifrost의 `/admin/api/services` 아래 엔드포인트가 모두 `require_admin` 의존성을 사용하기 때문에, 상세 화면의 버튼도 같은 기준으로 잠급니다.
- `super_admin`만 계정을 새로 만들거나 역할을 바꾸거나 삭제할 수 있습니다.
- `admin` 이상은 API 키 목록을 조회할 수 있고, `super_admin`만 키를 발급하거나 회전하거나 폐기할 수 있습니다.

이 화면단 권한 확인은 사용자 경험을 위한 장치일 뿐입니다. 실제 검증은 매 요청마다 Bifrost 게이트웨이와 Bidar 인증 서버가 다시 수행합니다. 마지막 남은 최고 관리자 계정을 삭제하려는 요청은 인증 서버가 거절하며, 프런트엔드는 이 판단을 대신하지 않습니다.

## 인증 흐름

인증에는 access 토큰과 refresh 토큰을 함께 사용합니다. `/auth/refresh` 요청만 refresh 토큰을 실어 보내고, 그 밖의 모든 요청은 access 토큰을 사용합니다. access 토큰이 401로 거절되면 `refreshAccessToken()`이 한 번만 조용히 갱신을 시도합니다. 그 시도마저 실패하면 로그인 화면으로 돌려보냅니다. 403은 로그인 화면으로 보내지 않고, 화면 안에서 권한이 부족하다는 안내를 보여줍니다. 이 흐름 전체는 `admin/src/services/api.ts`의 인터셉터가 구현합니다.

## 상태 표시 원칙

관리자 콘솔은 수집하지 않은 값을 0으로 채우지 않습니다. `OverviewStats`의 `users`, `api_requests`, `system` 필드는 게이트웨이가 애초에 제공하지 않는 값이라서 타입 자체가 `null`이고, 화면은 이 값을 "미수집"으로 표시합니다. 또한 각 화면은 마지막으로 데이터를 받아온 시각을 함께 보여주며, 90초 넘게 갱신되지 않으면 오래된 값이라고 표시합니다. 이 규칙은 `admin/src/components/StatusPanel.tsx`와 `admin/src/lib/datetime.ts`가 구현합니다. 같은 파일이 화면 갱신 주기를 30초로, 경과 시간 라벨의 재계산 주기를 15초로 정의합니다. 모든 시각은 KST로 표시하고 표기에 시간대를 함께 적습니다.

같은 원칙에 따라 운영 개요 화면에 있던 "인프라 이력" 카드는 삭제했습니다. 이 카드는 가상 머신의 퇴역 여부를 소스 코드에 직접 적어 둔 정적 문구였고, 콘솔이 조회할 수 있는 대체 정보원이 없습니다. 실제로 확인하지 않은 상태를 화면에 남겨 두면 조회 결과처럼 읽히기 때문에, 값을 0이나 임의의 문구로 채우지 않고 카드 자체를 없앴습니다.

## 등록부 재적재 실패를 알리는 방법

서비스를 등록하고 수정하고 삭제하는 요청은 데이터베이스에 먼저 변경을 확정한 다음 게이트웨이 등록부를 다시 적재합니다. 재적재가 실패해도 저장한 레코드는 되돌아가지 않기 때문에, 레코드는 저장되었지만 라우팅 표는 이전 상태에 머물러 있는 상황이 생깁니다. 게이트웨이는 이 상황을 `207 Multi-Status`와 `registry_reloaded: false`, 실패 원인을 담은 `registry_error`로 알려줍니다.

axios의 기본 `validateStatus`는 2xx를 모두 성공으로 판정하므로 207 응답에서는 예외가 발생하지 않습니다. 그래서 세 가지 요청 모두 응답 본문의 `registry_reloaded` 값을 직접 확인합니다. 이 판정과 화면에 표시할 문구는 `admin/src/lib/registry.ts`의 `describeRegistryOutcome()`이 한곳에서 만듭니다. 재적재에 성공하면 "등록부도 함께 다시 적재됐습니다"라는 문장을 성공 색으로 보여주고, 실패하면 저장은 끝났지만 등록부에는 반영되지 않았다는 사실을 경고 색으로 보여주면서 `registry_error` 문자열을 그대로 덧붙입니다. 경고 문구는 서비스 화면의 "등록부 다시 적재" 버튼으로 다시 시도하라고 안내하며, 그 버튼이 성공하면 경고를 지웁니다.

삭제는 조금 다르게 처리합니다. 삭제가 끝난 상세 화면은 더 이상 존재하지 않는 레코드를 다루고 있어서 그대로 두면 안 되므로, 판정 결과를 이동할 주소의 history state에 실어서 목록 화면으로 넘깁니다. 목록 화면은 그 값을 한 번만 읽어서 보여주고 history state를 비우기 때문에, 새로 고치거나 뒤로 이동해도 같은 문구가 다시 나타나지 않습니다.

## API 키 화면

API 키는 서비스와 서비스 사이에서 사용하는 자격 증명입니다. 인증 서버가 소유하고 게이트웨이가 중계하며, 하나의 계정에 묶입니다. 화면은 `/api-keys` 주소에 있고 사이드바 메뉴 이름은 "API 키"입니다.

목록은 키 이름과 접두 문자열, 소유자, 상태, 만료 시각, 마지막 사용 시각, 생성 시각을 한 행에 표시합니다. 접두 문자열은 평문 키의 앞 여덟 자이며 자격 증명이 아닙니다. 서버가 검증할 때 후보 행을 좁히는 용도이고, 운영자가 어느 키인지 알아보는 표식이기도 하므로 모노스페이스 글꼴로 적습니다. 목록 응답에는 소유자의 숫자 ID만 들어 있어서, 화면은 사용자 목록을 따로 조회해서 이름을 채웁니다. 이 조회가 실패하거나 아직 끝나지 않았으면 이름을 지어내지 않고 ID만 적습니다.

목록 위에는 필터가 두 개 있습니다. 소유자 필터는 화면에서 거르지 않고 `user_id` 질의 문자열로 서버에 넘겨서 좁힙니다. "활성 키만 보기"는 기본으로 켜져 있으며, 이 항목을 끄면 폐기된 키와 만료된 키도 함께 나열합니다.

### 상태를 세 가지로 나누어 판정하는 이유

서버는 `is_active`와 `expires_at`을 따로 보고하고 둘을 합쳐 주지 않습니다. 그래서 `is_active`가 아직 참인데도 만료 시각이 이미 지난 키가 존재하며, 플래그만 읽으면 인증 서버가 더 이상 받아 주지 않는 키를 활성이라고 적게 됩니다. 콘솔은 `admin/src/lib/apikeys.ts`의 `apiKeyState()`에서 세 가지로 판정합니다. 폐기 여부를 먼저 확인하고, 폐기되지 않은 키 가운데 만료 시각이 현재 시각 이하인 키를 만료로 판정하며, 나머지를 활성으로 판정합니다. 폐기를 먼저 보는 까닭은, 폐기는 저장된 사실이고 만료는 시계와 비교한 결과이기 때문입니다. 폐기된 키를 만료라고 적으면 운영자가 거두어들인 키를 스스로 수명을 다한 키로 읽게 됩니다.

시각 필드는 모두 시간대 표기가 없는 UTC 문자열입니다. 인증 서버의 `api_keys` 표가 `TIMESTAMP WITHOUT TIME ZONE` 자료형을 사용하기 때문입니다. 브라우저는 시간대 접미사가 없는 문자열을 현지 시각으로 읽으므로, 그대로 두면 KST 환경에서 모든 시각이 아홉 시간씩 어긋납니다. `admin/src/lib/datetime.ts`의 `parseServerDate()`가 접미사가 없는 값에 `Z`를 붙여서 UTC로 해석하고, 화면은 그 결과를 KST로 표시합니다. 만료 판정도 같은 함수를 거치므로 목록의 표기와 상태 배지가 서로 어긋나지 않습니다.

### 평문 키를 다루는 원칙

서버는 키의 요약값만 보관하므로 평문 키는 발급 응답과 회전 응답에 한 번씩만 들어 있고 다시 조회할 수 없습니다. 콘솔은 이 값을 React 상태에만 보관합니다. `localStorage`에 쓰지 않고, 주소 표시줄에 넣지 않으며, 로그로 출력하지도 않습니다.

발급에 성공하면 평문 키를 보여 주는 화면이 나타납니다. 이 화면에는 복사 버튼과 함께 창을 닫으면 다시 볼 수 없다는 경고를 적어 둡니다. 복사 버튼은 편의 장치일 뿐이므로 평문은 화면에도 그대로 출력하며, 브라우저가 클립보드 접근을 거절하면 그 사실을 문장으로 알리고 직접 선택해서 복사하라고 안내합니다. 이 창은 Escape 키로 닫히지 않습니다. 창 안에 있는 값이 평문의 유일한 사본이기 때문에, 닫기를 누르면 정말 닫을 것인지 한 번 더 확인한 다음에야 상태에서 지웁니다.

목록 응답과 상세 응답에는 평문도 요약값도 들어 있지 않습니다. 키를 잃어버렸다면 다시 볼 방법이 없으므로 회전하거나 새로 발급해서 교체해야 하며, 화면 아래쪽에 이 한계를 문장으로 적어 두었습니다.

### 회전과 폐기

회전은 새 키를 발급하면서 구 키를 같은 순간에 폐기합니다. 새 키는 이름과 소유자, 만료 시각을 그대로 물려받고 `id`와 접두 문자열은 새로 받습니다. 두 키가 함께 유효한 겹침 구간은 없습니다. 그래서 호출을 멈추지 않고 키를 바꾸려면 회전 대신 다음 순서를 따라야 합니다. 먼저 새 키를 발급하고, 호출자의 설정을 새 키로 교체하고, 교체가 끝난 다음에 구 키를 폐기합니다. 이 순서는 화면 위쪽의 안내와 회전 확인 대화 상자에 모두 적어 두었습니다. 이미 폐기된 키를 회전하려는 요청은 서버가 409로 거절하며, 화면은 폐기된 키의 회전 버튼과 폐기 버튼을 미리 잠급니다.

폐기 확인 대화 상자는 되돌릴 수 없다는 사실과, 이 키를 사용하는 호출자가 즉시 401을 받는다는 사실을 함께 적습니다. 폐기는 행을 지우지 않고 `is_active`를 거짓으로 바꾸는 작업이라서 응답은 본문이 없는 204가 아니라 폐기된 레코드를 담은 200입니다. 폐기에 성공하면 `invalidateQueries`로 목록 질의를 무효로 만들어 서버가 가진 상태로 다시 맞춥니다.

한 계정이 가질 수 있는 활성 키 개수에는 상한이 있습니다. 상한을 넘긴 발급 요청은 409와 함께 그 이유를 담은 `detail` 문자열을 받으며, 화면은 발급 대화 상자를 열어 둔 채 서버가 보낸 문구를 그대로 보여줍니다. 입력한 값도 그대로 남기 때문에 소유자만 바꾸어 다시 시도할 수 있습니다. 422는 FastAPI가 만드는 배열 형태의 `detail`이므로 `extractValidationDetail()`이 항목마다 "필드 이름: 사유" 형태로 바꾸어 한 줄로 보여줍니다.

만료 시각 입력은 `datetime-local` 형식이고 시간대가 없습니다. 브라우저는 이 값을 현지 시각으로 읽으며, 그것이 운영자가 의도한 시각입니다. `localInputToUtcIso()`가 그 순간을 UTC로 바꾸어 전송하므로 서버는 운영자가 고른 시점을 그대로 받습니다. 입력을 비워 두면 `expires_at`을 아예 보내지 않고, 서버는 이 경우를 만료가 없는 키로 읽습니다. 과거 시각은 서버가 422로 거절합니다.

`super_admin`이 아닌 계정에게는 발급과 회전, 폐기 버튼을 모두 잠그고 최고 관리자 계정이 필요하다는 안내를 보여줍니다. 다른 화면과 마찬가지로 이 잠금은 편의 장치이며, 최종 판정은 게이트웨이와 인증 서버가 매 요청마다 다시 내립니다.

## 백업 화면

백업 화면은 `GET /admin/api/observability/backups` 응답을 구성 요소별 카드와 원본 값 표로 보여줍니다. 이 응답은 백업 작업이 node exporter의 textfile collector로 내보낸 `bngdrasil_backup_` 계열 지표를 게이트웨이가 Prometheus에서 읽어 온 결과입니다. 각 구성 요소마다 마지막 성공 시각과 그 시각으로부터 지난 경과 시간, 마지막 실행 시각과 실행 결과, 미전송 개수를 함께 표시합니다. 실행 결과는 `bngdrasil_backup_last_run_status`를 따라 0을 성공으로, 1을 실패로 읽습니다.

서버가 `null`을 돌려준 항목은 "미보고"로 표시하고 0으로 바꾸지 않습니다. 예를 들어 오프사이트 전송을 담당하는 `ship` 구성 요소는 미전송 개수를 내보내지 않으며, 한 번도 성공한 적이 없는 구성 요소에는 마지막 성공 시각이 없습니다. 이 자리에 0을 적으면 측정한 적이 없는 값을 측정 결과처럼 읽게 되기 때문입니다.

경과 시간을 판정하는 임계값은 baedalus의 `monitoring/prometheus/rules/basic.yml`에 있는 경보 규칙과 같은 값을 사용합니다. 로컬 백업은 `BackupStale` 규칙을 따라 8시간, 오프사이트 전송은 `BackupShipStale` 규칙을 따라 14시간이 기준이며, 미전송 개수는 `BackupUnshippedPileup` 규칙을 따라 4개를 넘으면 경고로 표시합니다. 이 판정 함수들은 `admin/src/lib/backup.ts`에 모아 두었고 단위 시험으로 임계값을 고정해 두었기 때문에, 경보 규칙과 콘솔의 판단이 어긋나면 시험이 실패합니다.

Prometheus가 응답했지만 백업 시계열을 아직 하나도 갖고 있지 않으면 응답의 `available`이 `false`가 됩니다. 이때 화면은 카드를 하나도 그리지 않고, 지표가 아직 보고되지 않았다는 안내와 서버가 보낸 `note` 문장을 보여줍니다. 게이트웨이에 `PROMETHEUS_URL`이 설정되어 있지 않으면 501이 돌아오며, 화면은 설정을 추가하고 프로세스를 다시 시작해야 한다는 안내를 경고 색으로 표시합니다. Prometheus 조회 자체가 실패하면 502가 돌아오고, 화면은 게이트웨이가 보낸 `detail` 문자열을 그대로 보여주면서 다시 시도 버튼을 제공합니다. 화면 위쪽에는 Grafana의 백업 대시보드(`bngdrasil-backup`)로 이동하는 링크를 두어 시계열 추이를 확인할 수 있게 했습니다.

## 발화 중 알림

운영 개요 화면 위쪽의 "발화 중 알림" 구역은 `GET /admin/api/observability/alerts` 응답을 보여줍니다. 발화 건수와 등급별 건수를 먼저 적고, 알림마다 이름과 등급 배지, 대상 라벨, 발화가 시작된 뒤 지난 시간, `summary` 주석을 표로 나열합니다. Prometheus가 `pending` 상태로 보고한 알림은 아직 통지 대상이 아니기 때문에 서버가 제외하며, 화면도 그 사실을 문장으로 적어 둡니다.

이 구역은 개요 통계나 `/ready` 카드와 별개의 질의를 사용하므로, 두 요청이 실패해도 알림 목록은 그대로 나타납니다. 발화 중인 알림은 화면에서 가장 급한 정보이므로, 다른 엔드포인트의 실패 때문에 사라지면 안 되기 때문입니다.

각 알림의 `silenced`와 `inhibited` 값이 `true`이면 음소거와 억제 배지를 붙입니다. 두 값이 `null`이면 Alertmanager에 확인하지 못했다는 뜻이므로 "확인 불가"로 표시하고, 억제되지 않았다는 판정으로 바꾸어 적지 않습니다. 응답의 `alertmanager.configured`가 `true`인데 `available`이 `false`이면 Alertmanager 조회가 실패했다는 안내와 `error` 문자열을 함께 보여줍니다. `configured`가 `false`이면 게이트웨이에 `ALERTMANAGER_URL`이 설정되어 있지 않다는 사실을 적습니다. 발화 중인 알림이 한 건도 없다는 문장은 조회에 성공한 경우에만 표시하며, 501과 502는 백업 화면과 같은 방식으로 안내합니다. 이 구역에도 Grafana 개요 대시보드(`bngdrasil-overview`)로 이동하는 링크를 두었습니다.

## 게이트웨이 준비 상태와 저장된 검사 기록

운영 개요 화면의 "게이트웨이 준비 상태" 카드는 `GET /ready` 응답을 그대로 보여줍니다. 게이트웨이는 데이터베이스나 서비스 등록부 가운데 하나라도 준비되지 않으면 503으로 응답하지만, 그 본문에는 어느 쪽이 실패했는지 설명하는 값이 들어 있습니다. 그래서 `fetchReadiness()`는 axios의 `validateStatus`로 200과 503을 모두 정상 응답으로 받아서 본문을 읽고, `database_error`와 `registry_error` 문자열을 화면에 그대로 옮깁니다. 네트워크 연결이 끊겼거나 예상하지 못한 상태 코드가 돌아온 경우에만 오류 상태로 표시합니다. 이 카드 위쪽에 있는 등록부 카드는 관리자 API의 개요 통계에서 온 값이라서 출처가 다르며, 두 응답의 값을 하나로 합쳐서 보여주지 않습니다.

서비스 상세 화면의 "마지막으로 기록된 상태"는 `GET /admin/api/services/{id}/health` 응답입니다. 이 엔드포인트는 대상 서비스에 실제로 요청을 보내지 않고 데이터베이스에 저장된 마지막 결과를 돌려줍니다. 그래서 화면은 이 값을 지금 관측한 상태라고 말하지 않고, 기록된 상태와 그 확인 시각을 함께 보여줍니다. 지금 다시 검사하려면 `POST /admin/api/services/health-check-all`을 호출하는 "전체 서비스 상태 검사" 버튼을 사용해야 하며, 이 버튼은 한 서비스가 아니라 등록된 모든 서비스를 검사한다는 사실을 화면에 적어 두었습니다.

## 릴리스 정보

관리자 콘솔은 세 가지 빌드 정보를 서로 다른 화면에 나누어 표시합니다. 셋 모두 `version`과 `build_sha`, `build_time`, `build_ref`, `started_at`이라는 같은 형태를 사용하기 때문에, 표시 규칙은 `admin/src/lib/build.ts`와 `admin/src/components/BuildFacts.tsx` 한곳에 모아 두었습니다.

첫째는 게이트웨이 자신의 빌드입니다. 운영 개요 화면의 "게이트웨이 릴리스" 구역이 `GET /admin/api/settings/stats/overview` 응답의 `app` 블록을 그대로 보여줍니다. 이 블록은 Bifrost의 `src/core/buildinfo.py`가 만들고 루트 엔드포인트와 활성 상태 프로브도 같은 값을 보고하므로, 콘솔이 보는 커밋과 외부 프로브가 보는 커밋을 따로 맞추어 볼 필요가 없습니다. 커밋 SHA는 화면에 앞 열두 자만 적고 전체 값은 `title` 속성에 넣으며, 전체 값을 복사하는 버튼을 함께 둡니다. 브라우저가 클립보드 접근을 거절하면 전체 SHA를 화면에 출력해서 직접 선택할 수 있게 합니다. 기동 시각 옆에는 그 시각부터 지난 시간을 함께 적어서, 프로세스가 언제 다시 시작했는지 바로 읽을 수 있게 했습니다.

둘째는 업스트림 서비스의 빌드입니다. 서비스 상세 화면의 "마지막으로 기록된 상태" 구역이 `GET /admin/api/services/{id}/health` 응답의 `upstream_build`와 `build_observed_at`을 보여줍니다. 게이트웨이는 이 값을 데이터베이스에 저장하지 않고 프로브를 실행한 프로세스 안에만 들고 있습니다. 그래서 등록부를 다시 적재하거나 게이트웨이가 다시 시작하면 다음 검사 전까지 두 값이 모두 `null`이 되며, 화면은 이 상태를 "이 서비스는 빌드 정보를 보고하지 않거나 아직 프로브하지 않았습니다"라는 문장으로 적습니다. 다섯 항목이 모두 `null`인 객체도 같은 문장으로 처리합니다. 빈 칸 다섯 줄을 그리면 값을 관측했는데 비어 있다는 뜻으로 읽히기 때문입니다. "전체 서비스 상태 검사"를 실행하면 응답의 `details[서비스 이름]`에서 방금 관측한 값을 읽어 화면에 즉시 반영하고, 이어서 상세 질의를 무효로 만들어 서버가 가진 값으로 다시 맞춥니다. `details`는 예전 게이트웨이에 없는 필드이므로, 이 맵이 없으면 즉시 반영을 생략하고 질의 무효화만 수행합니다.

서비스 목록에는 커밋 SHA 열을 두지 않았습니다. 목록 API인 `GET /admin/api/services`가 빌드 정보를 제공하지 않기 때문에, 열을 만들면 모든 행이 비어 있거나 서비스마다 상세 요청을 한 번씩 더 보내야 합니다. 대신 상태 검사 결과 표 위에 빌드 정보는 상세 화면에서 확인하라는 안내를 적어 두었습니다.

셋째는 콘솔 자신의 빌드입니다. 운영 설정 화면의 "콘솔 빌드" 구역이 번들과 같은 경로에 있는 `/release.json`을 읽어서 커밋 SHA와 빌드 기준, 빌드 시각을 보여줍니다. 이 파일은 `.github/workflows/deploy.yml`의 빌드 단계가 `admin/dist/release.json`으로 만들며, 커밋 SHA는 체크아웃한 작업 트리에서 직접 읽기 때문에 과거 커밋을 다시 빌드하는 롤백 배포에서도 실제로 빌드한 커밋이 기록됩니다. 이 요청은 인증이 필요 없고 같은 출처에 있으므로 axios 인스턴스를 쓰지 않고 플랫폼의 `fetch`로 보냅니다. 파일이 없거나 응답이 JSON이 아니면 "미기록"으로 표시합니다. 로컬 개발과 스모크 시험에는 이 파일이 아예 없기 때문에 그 환경에서 미기록이 나타나는 것은 정상이며, 배포한 콘솔에서 미기록이 보인다면 배포 워크플로가 표식을 만들지 못했다는 뜻입니다.

`release.json`은 이름에 내용 해시가 붙지 않는 파일입니다. `nginx/nginx.conf`의 admin vhost는 `/assets/` 아래의 해시 파일만 1년 동안 캐시하고 나머지 정적 파일은 매 요청마다 재검증하는데, 확장자 목록을 사용하는 그 규칙에는 `.json`이 들어 있지 않아서 `release.json`은 어느 쪽에도 걸리지 않았습니다. 그대로 두면 `location /`의 SPA 대체 규칙에 걸려서 파일이 없을 때 404 대신 HTML 껍데기가 돌아옵니다. 그래서 두 vhost에 `location = /release.json` 블록을 추가해서 매 요청 재검증을 적용하고, 파일이 없으면 404로 응답하도록 했습니다.

VM1에 보관된 직전 릴리스, 다시 말해 롤백 지점은 이 화면이 표시하지 않습니다. 그 정보는 `scripts/vm1-release-static.sh`가 관리하는 `previous-<app>` 심볼릭 링크에만 있고 조회할 수 있는 API가 없기 때문입니다. 확인할 수 없는 값을 화면에 적으면 조회 결과처럼 읽히므로, 설정 화면에는 이 한계를 문장으로 적어 두었습니다.

## Grafana 링크

관측 화면은 지표를 직접 조회하지 않고 Grafana로 이동하는 링크만 만듭니다. 대시보드 링크는 baedalus가 배포한 대시보드의 고정 uid를 사용해 `d/{uid}` 주소로 바로 이동합니다. uid 목록과 각 대시보드가 받는 변수는 `admin/src/lib/grafana.ts`에 상수로 모아 두었고, `var-service` 변수를 선언한 대시보드에만 선택한 서비스를 전달합니다. 목록 화면인 `/dashboards`에는 템플릿 변수가 없어서 `var-service`를 붙여도 해석되지 않기 때문에, 그 주소로는 더 이상 이동하지 않습니다.

로그 탐색 링크에 들어가는 LogQL 선택자는 입력란으로 노출해서 직접 고칠 수 있게 했습니다. Loki의 `service` 라벨에는 Alloy가 컨테이너에서 읽어 온 compose 서비스 이름이 들어가지만, 서비스 선택 목록은 게이트웨이에 등록된 이름을 보여줍니다. 두 이름이 같다는 보장이 없고 콘솔은 그 대응 관계를 알 수 없기 때문에, 선택자를 정규 표현식으로 넓혀서 맞추는 대신 기본값만 채워 두고 어긋날 수 있다는 사실을 화면에 적었습니다.

## 단위 시험

`admin/`에는 vitest로 실행하는 단위 시험이 있습니다. `cd admin && npm ci && npm test`로 실행하며, `npm test`는 `vitest run`을 호출해서 한 번만 실행하고 끝납니다. 설정은 `admin/vitest.config.ts`에 있고, 시험 대상이 모두 순수 함수이기 때문에 DOM이 필요하지 않아서 node 환경으로 실행하며 jsdom을 설치하지 않았습니다. CI에서는 `.github/workflows/build.yml`이 lint 단계 뒤에서 admin에 한정해 같은 명령을 실행합니다.

시험 대상은 다음과 같습니다.

- `admin/src/services/api.ts`의 `extractDetail()`과 `extractValidationDetail()`: FastAPI가 돌려주는 422 본문과 문자열 `detail`, `message` 대체 경로를 해석하는 함수입니다. 이 함수가 실패하면 화면에는 서버가 거절한 이유 대신 axios의 기본 문구만 남기 때문에, 항목이 하나인 경우와 둘인 경우, `loc`에 `body`만 있는 경우, `loc`이 중첩된 경우, 항목이 비정상인 경우, 목록이 비어 있는 경우를 모두 고정해 두었습니다.
- `admin/src/lib/grafana.ts`: 대시보드 uid 목록과 `var-service` 변수를 붙이는 규칙을 확인합니다. 변수를 선언하지 않은 대시보드에 `var-service`를 넘기면 Grafana가 그 값을 무시하므로, 적용되지 않은 필터가 적용된 것처럼 보이지 않도록 규칙을 시험으로 고정했습니다.
- `admin/src/lib/backup.ts`: 백업 경과 시간과 임계값 판정, `last_run_status` 해석, 미전송 개수 판정, `null`을 0으로 바꾸지 않는 규칙을 확인합니다.
- `admin/src/lib/apikeys.ts`: API 키의 상태를 활성과 만료와 폐기로 나누는 판정, 만료가 없는 키를 만료로 읽지 않는 규칙, 폐기된 키를 만료로 바꾸어 적지 않는 규칙, `datetime-local` 입력을 UTC 시점으로 바꾸는 변환, 사용자 이름을 찾지 못했을 때 ID만 남기는 규칙을 고정해 두었습니다.
- `admin/src/lib/datetime.ts`: 시간대 표기가 없는 서버 시각을 UTC로 읽는지 확인합니다. 이 규칙이 무너지면 KST 환경에서 모든 시각이 아홉 시간씩 어긋나고 만료 판정까지 함께 틀어지기 때문에, 접미사가 있는 값과 없는 값, 해석할 수 없는 값을 모두 시험으로 고정했습니다.
- `admin/src/lib/registry.ts`: 등록부 재적재 결과에 따라 어떤 색과 문구를 고르는지 확인합니다.
- `admin/src/lib/build.ts`: 빌드 정보의 표시 규칙을 확인합니다. 빈 문자열을 기록된 값으로 읽지 않는지, 커밋 SHA를 몇 자로 줄이는지, 다섯 항목이 모두 `null`인 객체를 관측하지 못한 상태로 판정하는지, 기동 시각이 없을 때 경과 시간을 지어내지 않는지, `release.json`이 아닌 응답을 릴리스 표식으로 읽지 않는지를 고정해 두었습니다.
- `admin/src/services/api.http.test.ts`: 빌드 관련 응답을 실제 HTTP 왕복으로 해석합니다. `upstream_build`의 항목별 `null`과 객체 자체가 `null`인 경우, 두 필드가 아예 없는 예전 게이트웨이 응답, `details` 맵이 있는 검사 결과와 없는 검사 결과, 개요 통계의 `app` 블록을 각각 확인합니다. 같은 파일이 API 키 계약도 왕복으로 확인합니다. 목록 요청이 끝 슬래시를 유지하는지, 201 본문에서 평문 `key`를 읽는지, 만료를 고르지 않았을 때 `expires_at`을 아예 보내지 않는지, 폐기가 204가 아니라 폐기된 레코드를 담은 200인지, 상한 초과와 폐기된 키 회전이 각각 409로 돌아오는지, 성공 응답에 붙는 `Cache-Control: no-store` 헤더가 본문 해석을 바꾸지 않는지를 고정해 두었습니다.

화면 컴포넌트에서 판정 논리를 `admin/src/lib/` 아래로 옮겨 둔 이유도 여기에 있습니다. 순수 함수로 분리해 두면 브라우저를 띄우지 않고도 판정 규칙을 시험할 수 있습니다.

## 스모크 시험

단위 시험이 확인하지 못하는 부분은 화면이 실제로 그려지는 결과입니다. 그래서 `admin/e2e/` 아래에 Playwright로 실행하는 스모크 시험을 두었고, 이 시험은 개발 서버가 아니라 빌드 결과물을 Chromium으로 띄워서 확인합니다. 실행 방법과 CI 구성은 [로컬 개발](development.md) 문서에 적어 두었으며, 이 절에서는 무엇을 확인하는지와 목 게이트웨이가 무엇을 모사하는지를 설명합니다.

### 목 게이트웨이

`admin/e2e/mock-gateway.mjs`는 Node의 `http` 모듈만 사용하는 단일 파일 서버이며 의존성을 추가하지 않습니다. 운영 환경에서 콘솔은 게이트웨이 루트(`/auth/*`와 `/ready`)와 관리자 API(`/admin/api`)를 하나의 인그레스 뒤에서 호출하므로, 이 서버도 두 영역을 함께 응답합니다. 응답 형식은 Bifrost 저장소의 `src/schemas/*.py`와 `docs/admin-api.md`가 규정한 계약을 그대로 따르며, 특히 상태 코드만 보아서는 알 수 없는 세 가지를 실제 형식대로 재현합니다.

- 422 응답은 FastAPI가 만드는 배열 형태의 `detail`을 사용하고, 거절된 항목마다 하나씩 원소를 담습니다. 목 서버는 `admin/e2e/mock-gateway.mjs`에 Bifrost의 목적지 정책 일부를 옮겨 두었기 때문에, 시험이 루프백 주소나 잘못된 검사 경로를 입력하면 게이트웨이가 보냈을 문구가 그대로 돌아옵니다.
- 삭제 응답은 본문이 없는 204가 아니라 `service_id`와 `service_name`, 재적재 결과를 담은 200입니다.
- 등록부 재적재가 실패한 쓰기는 `207 Multi-Status`와 `registry_reloaded: false`로 응답합니다. axios는 207을 성공으로 판정하므로, 이 경우를 구분하는지 확인하려면 상태 코드가 아니라 본문을 읽어야 합니다.
- 업스트림 빌드 정보는 데이터베이스가 아니라 프로세스 안에만 있는 값이므로, 목 서버도 서비스 목록과 별개의 상태로 들고 있습니다. `POST /admin/api/services/health-check-all`이 이 상태를 갱신하고 그 결과를 `results`와 `details`에 함께 담으며, `GET /admin/api/services/{id}/health`는 같은 상태를 읽어서 응답에 덧붙입니다. 목 서버의 `blog` 서비스는 빌드 정보를 보고하지 않는 업스트림이라서, 검사를 실행한 뒤에도 두 필드가 `null`로 남습니다.

- API 키 경로는 끝 슬래시가 붙은 `/admin/api/api-keys/`를 사용하고, 슬래시가 없는 경로에는 FastAPI와 같이 307로 응답합니다. 목록에는 폐기된 키도 `is_active: false`로 남고, 발급과 회전만 평문 `key`를 담은 본문을 돌려주며, 폐기는 폐기된 레코드를 담은 200으로 응답합니다. 평문 키는 `bng_` 다음에 43자가 오는 형식으로 만들어서 인증 서버의 `secrets.token_urlsafe(32)` 결과와 같은 모양을 유지합니다. 목 서버는 활성 키 상한을 둘로 정해 두었기 때문에, 상한을 넘긴 발급이 409로 거절되는 장면을 클릭 한 번으로 확인할 수 있습니다.

시험이 보고 싶은 실패 상황은 `POST /__mode`로 전환합니다. 이 스위치는 `/ready`의 503 응답, 백업 요약의 501과 502와 `available: false`, 알림 요약의 501과 502와 Alertmanager 조회 실패, 쓰기의 등록부 재적재 실패를 각각 켤 수 있습니다. 여기에 `role` 스위치를 두어서 `/auth/me`가 보고하는 역할을 `admin`으로 바꿀 수 있습니다. 이 상태에서는 목 서버도 API 키 쓰기 요청을 403으로 거절하므로, 화면이 버튼을 잠그는 동작과 서버가 최종 판정을 내리는 동작을 함께 확인할 수 있습니다. 각 시험은 시작하기 전에 `POST /__reset`으로 서비스 목록과 스위치를 처음 상태로 되돌리므로, 앞선 시험이 남긴 상태를 물려받지 않습니다. 다만 목 서버가 이 상태를 한 프로세스 안에 들고 있기 때문에, Playwright 설정은 작업자를 하나로 고정해서 시험을 순서대로 실행합니다.

### 확인하는 시나리오

| 파일 | 확인하는 내용 |
|---|---|
| `admin/e2e/auth.spec.ts` | 로그인 양식으로 세션을 만들고 운영 개요로 이동하는 흐름, 자격 증명이 틀렸을 때 서버가 보낸 이유를 적는 동작, 저장된 토큰이 401로 거절되면 조용한 갱신까지 실패한 다음 로그인 화면으로 돌아가는 동작을 확인합니다. |
| `admin/e2e/dashboard.spec.ts` | 준비 상태 카드와 발화 중 알림 구역이 함께 나타나는지, 게이트웨이 릴리스 구역이 빌드 항목을 KST 시각과 열두 자로 줄인 커밋 SHA로 적는지, `/ready`가 503일 때 준비되지 않은 상태와 그 이유를 적는지, Alertmanager를 확인하지 못했을 때 억제 상태를 "확인 불가"로 적는지 확인합니다. |
| `admin/e2e/services.spec.ts` | 목록에서 상세로 들어가 422를 항목별 문구로 받고, 값을 고쳐 정상으로 수정하고, 삭제 대화 상자를 Escape로 닫은 다음 다시 열어 삭제하고, 목록이 갱신되는 흐름을 한 번에 확인합니다. 등록이 207을 받는 경우도 별도로 확인합니다. |
| `admin/e2e/backups.spec.ts` | 정상 응답과 `available: false`, 501과 502를 각각 어떻게 표시하는지 확인합니다. 미전송 개수를 보고하지 않는 `ship` 구성 요소가 0이 아니라 "미보고"로 나타나는지도 함께 확인합니다. |
| `admin/e2e/observability.spec.ts` | 대시보드 링크 여덟 개가 고정 uid 주소를 담고 있는지, `var-service` 변수를 선언한 대시보드에만 선택한 서비스가 전달되는지, 로그 탐색 링크의 선택자가 서비스 선택에 따라 바뀌는지 확인합니다. |
| `admin/e2e/release.spec.ts` | 상세 화면이 마지막 프로브가 읽은 업스트림 빌드를 보여주는지, 프로브한 적이 없는 서비스에는 그 사실을 적고 상태 검사를 실행한 뒤에 값을 채우는지, 업스트림이 빌드를 보고하지 않으면 검사한 뒤에도 같은 문장을 유지하는지, 설정 화면이 `release.json`이 없는 빌드를 "미기록"으로 적는지 확인합니다. |
| `admin/e2e/users.spec.ts` | 사용자 목록이 인증 서버가 돌려준 계정을 그대로 그리는지, 현재 로그인한 계정을 구분해서 표시하는지 확인합니다. |
| `admin/e2e/api-keys.spec.ts` | 목록이 활성과 만료와 폐기를 구분해서 그리는지, 소유자 필터가 서버 질의를 좁히는지 확인합니다. 발급한 평문 키를 한 번만 보여 주고 확인을 받은 다음 지우는 흐름, 그 값이 `localStorage`와 주소 표시줄에 남지 않는지, 목록이 곧바로 갱신되는지도 함께 확인합니다. 회전이 구 키를 폐기하면서 새 평문 키를 보여 주는지, 폐기가 목록에 반영되는지, 상한을 넘긴 발급이 서버가 보낸 409 사유를 그대로 적는지, `admin` 역할에서 발급과 회전과 폐기 버튼이 잠기는지도 확인합니다. |

로그인 흐름 자체를 확인하는 시험을 제외한 나머지 시험은 양식을 다시 채우지 않고 저장된 토큰을 미리 넣어 둔 상태에서 시작합니다. 콘솔은 화면을 불러올 때 저장소에 있는 토큰을 읽어서 세션을 복원하므로, 이 방식은 다시 방문한 운영자의 브라우저와 같은 상태입니다.

## 디자인 토큰

`admin/src/index.css`가 디자인 토큰을 한곳에 모아 정의하고, 각 화면은 클래스 이름만 사용합니다. 배경은 `--canvas`(`#f6f3f1`), 본문 글자는 `--ink`(`#242424`), 강조색은 `--accent`(`#2b59d1`)입니다. 연한 배경 위의 강조 텍스트는 명도 대비 4.5:1을 확보하려고 `--accent-strong`(`#23489f`)을 따로 둡니다. 상태 색은 `--success`, `--warning`, `--danger`로 구분합니다. 제목은 세리프 글꼴(`--font-title`), 본문은 시스템 글꼴(`--font-body`)을 사용하며, 웹 폰트를 내려받지 않습니다. 그림자와 유리 효과, 지속적인 애니메이션은 사용하지 않습니다.
